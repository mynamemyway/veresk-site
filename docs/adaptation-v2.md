## 0. Принятые архитектурные решения (контракт)

**0.1. Перевод всего проекта на `rem`.**
Шрифты, отступы (`padding`, `gap`, `margin`), физические размеры блоков (карточки, триггеры, медиа, высоты) — в `rem` (базовый `1rem` = размер шрифта корня). В `px` остаётся только то, что перечислено в 0.4.

**0.2. Reflow снизу, Zoom сверху.**
- **Снизу (`≤1280px`) — Reflow:** смена раскладок/структуры через `@media (в px)`.
- **База `1281–1499px`:** desktop-раскладка, масштаб `1×`.
- **Сверху (Zoom) — на крупных тирах:** `≥1500px` ×1.08, `≥1850px` ×1.3 — **исключительно** через `html { font-size }`. Раскладка не меняется, весь макет (текст + блоки) пропорционально растёт. *(План ранее писал ×1.4 — устарело.)*
- `transform: scale()` для layout **запрещён** (мылит растр, ломает позиционирование/скругления/анимации).

> ⚠️ **Расхождение с черновиком:** в черновике «Zoom с 1280px». Точнее — между 1280 и 1500 идёт обычная desktop-раскладка `1×`, а сам zoom стартует на крупных тирах `1500/1850`. Иначе «прыжок» на 1280 сломает 1440.

**0.3. `clamp()` — только в нижней зоне (`≤1280px`).**
Плавность шрифтов/текста на мобильных и планшетах. Выше 1280 `clamp` для **масштаба** не используется — иначе он перемножается с изменением корня (двойное масштабирование, см. 0.6).

> 📌 **Не исключение, а соблюдение правила:** `--section-pad-y: clamp(3rem, 2rem + 3.75vw, 5rem)` (отступы секций, §3.8) выше 1280 упирается в потолок `5rem` — там значение постоянно (не флюид), поэтому под 0.3 не попадает.

> ⚠️ **Уточнение к черновику:** «clamp отключается выше 1280» — правило для **масштабных** значений. Остаются исключения (не общий масштаб, а отдельные свойства):
> 1. защитная полоса `.hero-title` `(min-width:1024px) and (max-width:1499px)` (style.css:704–712) — H1 = **4.7% текстовой колонки** (`cqw`, контейнер `.hero-headline-block`) с полом `clamp(1.7rem, 4.7cqw, var(--fs-h1))` (пол `27.2px` удерживает H1 выше H2 = 24 в зоне 1024–1111, см. §3.5); на ≥1850 остаётся в `px` (см. §5.5.5);
> 2. `geo-map height` `clamp(17.5rem, 46vw, 32.5rem)` (style.css:3310) — **не меняем**, растёт с корнем;
> 3. **иерархия заголовков** `@media (min-width:601px) and (max-width:1399px)` (style.css:122–126): `--fs-h2: clamp(1.5rem, 2.15vw, 2rem)`, `--fs-h3: clamp(1.25rem, calc(0.27rem + 1.41vw), 1.5rem)`, `--fs-h4: clamp(1.125rem, calc(0.14rem + 1.41vw), 1.375rem)` — иначе на планшетах/ноутбуках H2 (`2rem`) оказывался **больше** H1. Это единственный `clamp` **выше** 1280 (зона 1281–1399). Нижняя граница `601` — из тирового набора (там же заканчивается мобильный `clamp` с потолком 24px, без пола `1.5rem` на 601 была бы ступенька 24 → 22); верхняя **`1399` — производная**, не тировая: с `1400` H2 снова `2rem = 32px` и уже меньше H1 (там H1 ≈ 33.8px). Схлопнуть к тиру `1280` нельзя (сломает 1281–1399), к `1500` — тоже (изменит 1440: H2 32 → 31px).

**0.4. Что остаётся в `px` (не масштабируется).**
- Бордюры/разделители/хайрлайны `1px`.
- **Брейкпоинты в `@media`** — всегда `px` (в `@media` единицы `rem`/`em` считаются от начального 16px, а **не** от `html font-size` → не следуют за zoom).
- Значения, привязанные к вьюпорту: `vh`/`vw` (напр. высота вертикальной линии), `ch`-ограничения длины строк.

**0.5. a11y корневого шрифта.**
`html { font-size }` задаётся **от пользовательского дефолта**, а не фиксированным `px`: `calc(100% * k)`. Так масштаб умножает пользовательскую настройку размера шрифта и не ломает доступность. Задавать `html { font-size: 16px }` — нельзя.

**0.6. Один уровень флюида.**
Масштабом рулит **либо** корень, **либо** `clamp` на элементах — не оба на одном свойстве. На нижней зоне — `clamp`; на крупных тирах — корень.

**0.7. Анимация.**
Координаты анимаций — в той же системе единиц (`rem`), либо считаются от **фактической геометрии** элемента/контейнера (`getBoundingClientRect`), а не от хардкода пикселей под конкретную ширину. Тогда zoom безопасен и анимация «встаёт» на всех тирах.

**0.8. Типографические токены-роли.**
Ограниченный набор ролей (`--fs-h1 … --fs-label`) в `rem` — единый источник правды; все элементы маппятся на роли. **Одна роль = один класс** (см. §5.3.4).

## 1. Как сейчас реализована адаптация (факты)

**Подход:** desktop-first, почти все правила — `@media (max-width: …)`. Тир для больших экранов сейчас присутствует частично (переходный `--type-scale` на `≥1500/≥1850`).

**Брейкпоинты унифицированы** до набора `480 / 600 / 768 / 1024 / 1280 / 1500 / 1850` (+ один **производный** порог `1399` для иерархии заголовков — см. §0.3.3, §5.2).

**Контейнеры:** `--container-max: 75rem`, `--gutter: 2rem` (style.css:92–93); `.calc-container` берёт его из токена; у `.hero-section` — `max-width: calc(var(--hero-max) + 2 * var(--gutter))` (style.css:544) (**hero уже зажат в контейнер**, §5.1 выполнен). Внутренние ограничения (`51.25rem` у FAQ, `37.5rem` у `.calc-subtitle`, `60ch` в отзывах) — не трогать.

**Сетки:** CSS Grid + Flexbox — плюс, сохраняем.

**Типографика:** фиксированные `px` + множитель `--type-scale` (масштабировал **только шрифты** → отсюда «кривой» zoom). `clamp` — точечно (hero-h1, футер, `geo-map height`, один B2B-текст).

**Уже сделано:** семантические заголовки приведены к системе (уровни по коду): **H1** `.hero-title`; **H2** `.section-title`; **H3** `.section-subtitle`, `.card-title`, `.v2-group-title`, `.v2-step-title`, `.faq-heading`; **H4** `.card-label` (убраны локальные `.calc-title`/`.why-we-title`).

**Прочее:** `rem` = 16px (`html` font-size не задан); `box-sizing` глобальный; `:root` с токенами/темами; 1 container query; `viewport meta` корректная.

## 2. Проблемы именно для 1920×1080

1. Выше ~1400px вёрстка «растягивается», а не масштабируется — нет верхней границы у hero.
2. Рассогласование: hero во всю ширь, остальное в 1200px → разный ритм; вертикальная линия 58.33% уходит от контента.
3. `--type-scale` масштабировал только шрифты → блоки и анимации разъезжались.
4. До унификации не было единой системы брейкпоинтов.

## 3. Целевая модель (сводно)

- **Единый контейнер** для всех секций (в т.ч. hero).
- **Единый набор брейкпоинтов** (готов).
- **Reflow снизу / Zoom сверху** (0.2).
- **Токены-роли типографики** в `rem` (0.8).
- **Fluid-отступы секций** через `clamp()` (нижняя зона).
- **Ограничение длины строк** абзацев (`~65–75ch`) на широких экранах.
- **Вертикальный разделитель** привязан к контейнеру.

## 4. Фирменная логика скруглений при перекомпоновке (инвариант — не ломать)

> «Сохранить фирменную логику скругления углов при перекомпоновке объектов для разных разрешений: когда в стопку — меняются углы для скругления.» — Alex

**Суть паттерна.** Объекты, стоящие встык (тонкий стык 3px или общая рамка), читаются как **единый блок**. Скругляются только **внешние** углы группы (те, что граничат с фоном секции), внутренние стыки — **прямые**. Когда раскладка меняется (ряд → стопка, другая сетка), «внешними» становятся другие углы, и вёрстка **пересчитывает** скругления под новую геометрию. В каждом брейкпоинте перекомпоновки углы сначала **обнуляются** (`border-radius: 0`), затем назначаются заново — иначе правила прошлого тира наследуются каскадом.

**Где реализовано (карта для регресса):**

| Компонент | Раскладки и как меняются углы | Строки |
|---|---|---|
| Каталог `.pest-card` / `.pest-grid` | десктоп 6×1 (левый край первой, правый последней) → планшет 3×2 (4 внешних угла верх./ниж. ряда) → моб. 3 колонки; обнуление в каждом тире | 1946, 1977–1983, 2068–2086 |
| Прайс `.price-card` / `.prices-grid` | 3×1, только внешние углы; логика снимается ≤1024 | 1268–1277, 1289 |
| Калькулятор `.v2-prices` / `.v2-calc` | пара карточек, внешние углы только ≥1025 | 1556–1560 |
| «Почему мы» `.why-we-step` / `.why-we-mark` | слитное поле; заливка-маркер зеркалит нижний правый угол (`border-bottom-right-radius`) | 2165, 2182 |
| «Почему мы» `.why-we-card` | 2×2 → 1×4 (верх первой / низ последней) | 2244–2256, 2478–2488 |
| Note-блок `.why-we-note-text` / `.why-we-note-actions` / `.why-we-note-tg` | в ряд: `12px 0 0 12px` + `0 0.75rem 0.75rem 0` + скос на tg `::before` → в колонку: текст `12px 12px 0 0`, монолит `0 0 12px 12px`, tg без скоса | 2332, 2348, 2438–2454 |
| B2B `.b2b-tag` / `.b2b-tags` | 2×3 (4 внешних угла) → в колонку (верх/низ) | 2631, 2643–2655, 2795–2813 |
| CTA hero `.cta-deal` / `.cta-discount` | слитная плашка; красный бейдж зеркалит угол и перекрывает рамку через negative-margin | 802, 823 |
| Hero-фото `.image-container-block` | асимметричное скругление `--radius-asym: 2rem 0.5rem 2rem 2rem` | 81, 704 |
| Отзывы `.review-card` / `.reviews-track` | внешние края ленты; управляются JS-классами `.is-edge-start/end` (до инициализации — `:first/last-child`) | 3134–3150 |
| Футер `.footer-grid` | **скругления нет** (`border-radius` отсутствует у всех футерных селекторов) — правило секции к футеру не применяется | 3274 |

**Инварианты при адаптации под 1920 и рефакторинге:**
1. В каждом брейкпоинте перекомпоновки — сначала обнулить углы, потом назначить внешние.
2. «Внешний» угол — на границе группы с фоном; внутренние стыки всегда прямые.
3. При изменении числа колонок на крупном тире (напр. 1920) — пересчитать, какие элементы становятся угловыми (`:nth-child`, при динамике — JS-классы).
4. Слитные «поля»: скругление — на контейнере, заливка-бейдж зеркалит угол дочерним `border-*-radius`.
5. Где логика на negative-margin бейджа (`.cta-discount`) — **не** прятать родителя `overflow: hidden`, это сломает перекрытие рамки.
6. Единый источник значений — `--radius-main` / `--radius-asym`; при fluid-скруглении сохранять принцип «внешний/внутренний».
7. **`--radius-*` тоже переводим в `rem`** → скругления масштабируются вместе с zoom (согласованно с 0.1). Бордюр `1px` при этом остаётся `px` (0.4).

### 5.3. Типографика: токены-роли → rem → Reflow/Zoom

> Порядок принципиален: **сначала зафиксировать токены из текущих значений (без визуальных изменений), затем менять механизм.** Иначе не понять, что сломалось — токены или масштаб.

3.1. **Инвентаризация.** ✅ **ВЫПОЛНЕНО.** Собран инвентарь фиксированных `px` по всем правилам: `font-size`; геометрические значения (`padding`/`gap`/`margin`/размеры блоков/`--radius`), включая `px` внутри медиазапросов; отдельно отмечены `px`-исключения (бордюры/хайрлайны, тени, `blur()`, `vw`/`vh`, `ch`, брейкпоинты). Итог в `style.css`: остаётся **1** `font-size` в `px` (`clamp(32px, 2.5vw, 39px)`, H1 на ≥1850) и **139 `px`-значений** всего (без комментариев; 40 из них — бордюры `1px`, остальное — исключения по 0.4). Источник — `docs/text-set.md`.

3.2. **Токены-роли (rem), без смены вида.** ✅ **ВЫПОЛНЕНО.** Только 7 ролей шрифта добавлены в `:root` и применены в местах **точного** совпадения значения (см. 3.10): `--fs-h1 … --fs-h4`, `--fs-body`, `--fs-small`, `--fs-label`. Токены блоков (`--card-pad` и т.п.) **не заводились** — размеры не консолидировались. Результат — **нулевой визуальный дифф** (чистый рефактор).

3.3. **Перевод размеров на `rem`.** ✅ **ВЫПОЛНЕНО.** Механический перевод `calc(Npx * var(--type-scale))` → `(N/16)rem` и геометрических `px` → `rem` (comment-aware скрипт, исключения по 3.10 сохранены). Объём — коммит `4119ae5`: `232+ / 219−`. При `html font-size: 16px` вид идентичен.

3.4. **Одна роль = один класс.** ✅ **ВЫПОЛНЕНО.** `.why-we-card .card-title` (капс-лейбл преимуществ) вынесен в отдельную роль-класс `.card-label` (`font-size: var(--fs-label)`), контекстный оверрайд удалён; 4× `h4` в «Почему мы» переведены на `class="card-label"`. Нулевой визуальный дифф.

3.5. **Плавная типографика H1–H4 через `clamp()`.** ✅ **ВЫПОЛНЕНО** (коммиты `cf8fb97`, `bd0d5a2` — пол H1 `1.7rem`). Все четыре роли переведены на `clamp(min, линейная_функция_от_vw, max)` с **общим окном роста 420→480**: до 420 держится `min` (равен прежнему значению тира ≤480), с 481 — плоская полка. Значения «станет» (root 1×):

3.8. **Отступы секций:** ✅ **ВЫПОЛНЕНО.** Введён токен `--section-pad-y: clamp(3rem, 2rem + 3.75vw, 5rem)` (style.css:57) и применён в `.hero-section` (style.css:551), `.calc-section` (1229) и в стыке с полосой вереска `calc(var(--section-pad-y) + 60px)` (1238). Инвентарь абзацев (`~ch` — приблизительно, по средней ширине глифа; соотношение «ширина колонки / размер шрифта» **постоянно на всех разрешениях**, т.к. и контейнер, и шрифт — в `rem`, поэтому ширина строки не зависит от тира):

3.10. **Согласованные решения (реализация 3.2–3.3):**
   - Токены-роли — только 7 (`--fs-h1…h4`, `--fs-body`, `--fs-small`, `--fs-label`); применяем только при **точном** совпадении значения; размеры **не** консолидируем (ради пиксель-в-пиксель 1440).

   - Инвентарь покрывает и `px` **внутри** медиазапросов (мобильные) — тоже → `rem` (ниже 1280 нулевой дифф).
   - Контейнер: единый `--container-max: 75rem`; пер-тировые `1360px/1536px` — ✅ **удалены**.

   - Вересковое поле `60px` — **остаётся `px`** (завязано на JS и `calc`: style.css:563, 1043, 1238, 1245); кандидат на §5.5.

   - Базовое `html { font-size: 100% }` + тиры `≥1500px` ×1.08 и `≥1850px` ×1.3 — ✅ **сделано**; `--type-scale` — **0 вхождений**.

5.1. Hero: ширина ограничена, картинка масштабируется, разделитель на месте.
5.2. «Воздух» секциям и рост типографики обеспечиваются **корнем** (0.2/3.6), а не точечными правками.
5.3. **Контейнер — один `rem`.** Пер-тировые `--container-max: 1360px/1536px` — ✅ **удалены**; оставлен единый `--container-max: 75rem`. ### Риски / ограничения
- **Двойной флюид** (0.6): `clamp` + корень на одном свойстве = непредсказуемый размер. Контролировать.
- **a11y корня** (0.5): фиксированный `px` в `html font-size` запрещён.
- **Медиа-запросы в `rem`** не следуют за zoom → брейкпоинты только `px`.
- **Миграция `px`→`rem`** крупная: пропущенный `px` «отваливается» от общего масштаба → нужен инвентарь (3.1) и проверка на `1500/1850`.
- **`clamp()` требует реперов** (min/max), иначе «плавающие» размеры.
- **Анимации:** хардкод пиксельных координат ломается при zoom → переводить на `rem`/геометрию (0.7).
- **Крупный тир — только Zoom**, не перекомпоновка: число колонок сохраняется (иначе пересчитывать углы, см. раздел 4).
- **Исключение из унификации ширины:** локальные ограничения ширины внутренних текстовых элементов (`.calc-subtitle` `37.5rem`, FAQ-ответ `51.25rem`, отзывы `60ch`) — **не** разнобой контейнеров; на глобальный `--container-max` переводить **запрещено**. Унификации подлежат только внешние обёртки секций (`.hero-section`, `.calc-container`).

## Правила

1. **Никаких браузерных/автоматизационных инструментов и скриншотов** — рассуждаем только по коду.
2. **1440 — пиксель-в-пиксель**; менять только по явной просьбе.
3. **Не действовать сверх задания:** меняем строго то, что просят. Любое побочное последствие — сначала предупредить / предложить, не решать самому.
4. **Баг ≠ кэш:** пользователь всегда делает hard-reload перед проверкой вёрстки.
5. **Инвариант скруглений** — раздел «Фирменная логика скруглений» (сохранить).
6. **Комментарии в коде — на русском**; больших комментариев без необходимости не плодить, всё должно быть технично и лаконично, ведём код к чистоте.
7. **Порядок:** фазы по плану; перед каждой — сверка с этим файлом; после — регресс (grep + баланс скобок/комментариев).
